    96	 *
    97	 * Root cause (docs/rootcause-invalid-base64-json-header-2026-06-24.md):
    98	 * mppx 0.7.0's `x402Challenges` decodes the WHOLE `payment-required`
    99	 * header against a strict EVM-only schema. If ANY `accepts[]` offer
   100	 * carries an unrecognized network (e.g. a merchant that added a
   101	 * `solana:...` offer), the decode throws `InvalidJsonHeaderError`
   102	 * ("Invalid base64 JSON header.") and — because mppx spreads the
   103	 * www-authenticate and x402 challenge lists into one array literal —
   104	 * the throw discards the perfectly usable `www-authenticate` (Tempo)
   105	 * challenge too. The router then 502s with "Merchant payment failed".
   106	 *
   107	 * This wrapper sits UNDER the mppx client (passed as `config.fetch`),
   108	 * so it sees the raw upstream 402 before mppx parses it. On a 402 it
   109	 * drops any `payment-required` offer mppx can't parse, then validates
   110	 * the rewrite using mppx's OWN parser as the oracle:
   111	 *   - rewrite parses cleanly  → forward the rewritten response
   112	 *   - rewrite still fails AND a www-authenticate header is present
   113	 *                             → strip payment-required entirely, let
   114	 *                               mppx fall back to the Tempo challenge

   116	 *                               so mppx surfaces its own real error
   117	 *                               (we never silently swallow).

   120	 * legacySession — there is no `evm/charge` method — so retained eip155

   123	 * www-authenticate pays the same Tempo challenge the proxy already
